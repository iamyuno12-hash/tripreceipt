# OCR 엔진 조사 및 선택 근거

조사일: 2026-11-06

제안서에서 확정한 OCR 엔진은 **PaddleOCR** 이다. 제안서는 Flask 서버에서 파이썬
PaddleOCR 을 돌리는 구성이었고, 지금은 백엔드 없이 브라우저에서 직접 추론한다.
이 문서는 그 전환에 필요한 조사 결과와 결정을 기록한다. (최종보고서의 근거 자료)

## 1. 브라우저에서 PaddleOCR 을 돌리는 방법

PaddleOCR 공식 저장소가 **브라우저 배포용 SDK** 를 제공한다.

| 항목 | 값 |
|---|---|
| 패키지 | `@paddleocr/paddleocr-js` 0.4.2 |
| 라이선스 | Apache-2.0 |
| 추론 엔진 | ONNX Runtime Web (WASM, WebGPU 선택 가능) |
| 이미지 처리 | OpenCV.js (`@techstark/opencv-js` 4.10.0, 의존성에 포함) |
| 기준 모델 | PP-OCRv5 |

**선택 이유**

1. 공식 지원 경로다. 비공식 래퍼를 쓰지 않아도 된다.
2. **제안서의 OpenCV 전처리를 그대로 쓸 수 있다.** SDK 가 OpenCV.js 를 이미 의존성으로
   포함하므로 별도 설치 없이 같은 인스턴스로 전처리 파이프라인을 짤 수 있다.
3. **PP-OCRv5 기준이라 한국어 모델이 그대로 맞는다** (아래 2절).

### 모바일(안드로이드) 안을 접은 이유

중간에 안드로이드 앱으로 검토했을 때는 공식 안드로이드 SDK 가 **PP-OCRv6** 기준이었다.
그런데 PP-OCRv6 가 지원하는 50개 언어는 중국어·영어·일본어 + 라틴 문자 46개이고
**한글은 사전에 없다.** 한국어를 쓰려면 PP-OCRv5 계열 한국어 모델을 v6용 SDK 에 끼워야 해서
전처리·CTC 디코딩 호환성을 따로 검증해야 하는 부담이 있었다.

웹 SDK 는 PP-OCRv5 기준이므로 이 문제가 발생하지 않는다. **웹 전환으로 리스크가 사라진 셈이다.**

## 2. 사용할 모델

SDK 는 모델을 **압축하지 않은 `.tar`** 로 받는다. tar 안에 `inference.onnx` 와
`inference.yml` 이 있어야 하고, yml 의 `model_name` 이 코드에서 넘기는 이름과 **정확히**
같아야 한다. 다르면 초기화 단계에서 바로 오류가 난다.

공식 HuggingFace 저장소가 이 형식 그대로 제공한다. (둘 다 Apache-2.0)

| 역할 | 저장소 | `model_name` | 용량 |
|---|---|---|---|
| 검출 | `PaddlePaddle/PP-OCRv5_mobile_det_onnx` | `PP-OCRv5_mobile_det` | 4.6MB |
| 인식(한국어) | `PaddlePaddle/korean_PP-OCRv5_mobile_rec_onnx` | `korean_PP-OCRv5_mobile_rec` | 12.8MB |
| 인식(일본어·중국어·영어) | `PaddlePaddle/PP-OCRv5_mobile_rec_onnx` | `PP-OCRv5_mobile_rec` | 16.7MB |

확인된 세부 사항

- 검출 모델 후처리는 `DBPostProcess`, 언어와 무관하므로 모든 여행에서 공용으로 쓴다.
- 인식 모델 후처리는 `CTCLabelDecode` 이고, **문자 사전 11,945자가 `inference.yml` 안에
  들어 있다.** 별도 사전 파일(`ppocrv5_korean_dict.txt`)을 따로 관리할 필요가 없다.
- 여행 언어에 맞는 인식 모델 하나와 검출 모델만 내려받는다 (한국어 17.4MB, 일본어·중국어 21.3MB). 첫 인식 때만 받고 이후에는 브라우저 캐시를 쓴다.
- 일본어·중국어 모델은 한글을 읽지 못하고, 한국어 모델은 일본어 가나·한자를 읽지 못한다 → 여행마다 언어를 고른다 (3.9·3.10).

모델 파일은 용량이 커서 git 에 올리지 않는다. `scripts/fetch-models.sh` 가 내려받아
`.tar` 로 묶고 `model_name` 까지 검증한다. 코드 쪽 상수는 `src/ocr/models.ts` 에 있다.

## 3. 성능 관련 설정

### cross-origin isolation (중요)

ONNX Runtime Web 의 멀티스레드 WASM 은 `SharedArrayBuffer` 를 쓰고, 이것은
**cross-origin isolation 이 걸린 페이지에서만** 허용된다. 서버가 아래 두 헤더를
내려주지 않으면 단일 스레드로 떨어져 추론이 크게 느려진다.

```
Cross-Origin-Opener-Policy: same-origin
Cross-Origin-Embedder-Policy: require-corp
```

이 설정은 **두 곳에 있고 항상 같이 유지해야 한다.**

- 개발 서버: `vite.config.ts`
- 배포 서버: `docker/nginx.conf`

P0 의 환경 점검 화면에서 적용 여부를 바로 확인할 수 있다.

### 그 외

- ~~입력 이미지 긴 변을 960px 정도로 줄인 뒤 검출에 넣는다~~ → **틀린 가정이었다.** SDK 에 내장된 OCR 파이프라인 설정은
  `limit_side_len: 64, limit_type: min, max_side_limit: 4000` 이다. 짧은 변이 64px 보다 작을 때만 키우고, 그 외에는
  **원본 해상도 그대로(긴 변 최대 4000px) 검출한다.** 그래서 이미지 크기가 곧 검출 시간이고, 전처리에서 크기를
  줄이는 것이 속도에 직접 효과가 있다 (3.8·3.9 절)
- WebGPU 를 쓸 수 있는 환경이면 WASM 대신 선택할 수 있다. P4 에서 두 백엔드 처리시간을
  비교해 기록한다 (보고서 자료)
- `predict()` 가 `detMs` / `recMs` / `totalMs` 를 돌려주므로 측정에 따로 코드가 필요 없다

## 3.5 선검증 결과 — 합성 이미지 (2026-11-13)

> **주의**: 이 절과 3.6 절은 코드로 그린 합성 영수증 1장으로 측정한 결과다.
> 실제 사진 5장으로 다시 측정한 결과는 3.7·3.8 절이며, **전처리 결론은 3.8 절이 우선한다.**

P4 착수 전에 실제 브라우저(Chromium, 헤드리스)에서 한국어 인식이 되는지 확인했다.
진단 화면은 저장소에 남아 있다: **설정 > OCR 테스트** (`#/settings/ocr-test`).

테스트 이미지는 합성한 한국어 영수증 2장이다. 하나는 또렷한 상태, 하나는 감열지 열화를
흉내낸 것(대비 압축, 가우시안 블러, 노이즈, 3.2도 기울기).

| 항목 | 깨끗한 영수증 | 기울어진 감열지 |
|---|---|---|
| 평균 신뢰도 | 99% | 98% |
| 인식한 줄 | 38 | 38 |
| 전체 처리 시간 | 4,598ms | 4,835ms |
| 검출 / 인식 | 1,720 / 2,850ms | 1,640 / 3,138ms |
| 한국어 품목명 | 전부 정확 | 전부 정확 |

- `korean_PP-OCRv5_mobile_rec` 가 공식 SDK 에 그대로 로드된다. 전처리·디코딩 호환 문제 없음.
- `crossOriginIsolated = true` 확인, 멀티스레드 WASM 활성.
- 저대비·노이즈만으로는 인식률이 거의 떨어지지 않는다.

### 중요: 기울기는 인식률이 아니라 **파싱**을 깨뜨린다

인식 자체는 기울어져도 잘 된다. 문제는 그다음 단계다. 품목명·수량·금액이 각각 별도
검출 박스로 나오므로, 같은 줄에 속한 것끼리 y좌표로 묶어야 한다(제안서의 라인 그룹핑).
기울어지면 이 묶기가 성립하지 않는다.

| | 한 줄 안의 y 편차 | 줄 사이 간격 | 고정 임계값으로 분리 |
|---|---|---|---|
| 깨끗한 영수증 | 1~3px | 31~33px | 가능 (임계값 4~30px 아무거나) |
| 3.2도 기울어짐 | 25~27px | 7~10px | **불가능** |

기울면 한 줄 안의 편차가 줄 사이 간격보다 커져, 어떤 임계값을 써도 인접한 줄이 섞인다.

**결론: P3 의 기울기 보정은 P5 파서의 전제조건이다.** 보정 후 위 수치를 같은 방법으로
다시 측정해 비교표를 만든다 (P7 산출물).

## 3.6 전처리 효과 측정 — 합성 이미지 (2026-11-13)

> 3.7 절에서 실제 사진으로 검증한 결과, 여기서 쓴 OpenCV 기울기 보정은 실제 사진에서
> **동작하지 않았다.** 아래 표는 합성 이미지에서만 유효하다.

3.5 절에서 기울기가 줄 묶기를 깨뜨린다는 것을 확인했으므로, 전처리 단계별 효과를
같은 방법으로 측정했다. 측정은 **설정 > OCR 테스트** 화면에서 재현할 수 있다.

판정 기준은 "한 줄 안의 y 편차 < 줄 사이 간격" 이다. 이 조건이 깨지면 고정 임계값으로
품목·수량·금액을 같은 줄로 묶을 수 없다. 묶인 줄 수도 함께 본다 — 이 영수증의
정답은 **18줄**이다 (깨끗한 영수증을 전처리 없이 넣었을 때의 값).

### 기울어진 감열지 영수증 (3.2도)

| 전처리 | 줄 묶기 | 한 줄 편차 | 줄 간격 | 잔여 기울기 | 묶인 줄 | 신뢰도 | 처리시간 |
|---|---|---|---|---|---|---|---|
| 없음 | **불가** | 11px | 11px | 3.0도 | 27 | 98% | 4,305ms |
| 대비개선만 | 가능 | 12px | 23px | 3.2도 | 23 | 97% | 2,810ms |
| **기울기 보정만** | **가능** | **3px** | **27px** | **0.0도** | **18** | **99%** | 2,994ms |
| 보정 + 대비개선 | 가능 | 3px | 28px | 0.0도 | 18 | 96% | 3,205ms |
| 보정 + 대비 + 이진화 | 가능 | 4px | 31px | 0.0도 | 12 | 79% | 5,140ms |

### 깨끗한 영수증 (대조군)

| 전처리 | 줄 묶기 | 한 줄 편차 | 줄 간격 | 잔여 기울기 | 묶인 줄 | 신뢰도 |
|---|---|---|---|---|---|---|
| 없음 | 가능 | 3px | 27px | 0.0도 | 18 | 99% |
| 보정 + 대비개선 | 가능 | 3px | 27px | 0.0도 | 18 | 99% |

### 읽는 법

1. **기울기 보정이 결정적이다.** 보정 후 기울어진 영수증의 수치가 깨끗한 영수증과
   완전히 같아진다(3px / 27px / 18줄). 즉 보정이 기울기의 영향을 사실상 제거한다.
2. **"줄 묶기 가능" 만으로는 부족하다.** 대비개선만 적용한 경우 판정은 통과하지만
   23줄로 묶여 정답(18줄)과 다르다. 기울어진 상태에서는 한 줄이 여러 개로 쪼개진다.
   잔여 기울기와 묶인 줄 수를 함께 봐야 한다.
3. **이진화는 해롭다.** 신뢰도가 79% 로 떨어지고 12줄만 남는다(글자 소실). 처리시간도
   가장 길다. 감열지의 흐린 글자를 배경으로 날려버리기 때문으로 보인다.
4. **대비개선은 이 테스트에서 근거가 없다.** 보정만 했을 때 99%, 대비까지 더하면 96%.
   기본값에서 껐다.

### 한계

측정에 쓴 영수증은 합성 이미지 1장이다. 실제 감열지를 손으로 찍은 사진은 조명이
고르지 않아 대비개선이 유리할 수 있다. P7 에서 실제 영수증 여러 장으로 다시 측정하고,
그 결과를 최종보고서의 정량 근거로 쓴다.

## 3.7 실제 영수증 검증 (2026-11-13)

> **철회**: 이 절에 처음 적었던 "품목명 글자 일치율"(81.4% → 94.9% 등)과 "같은 줄" 수치는
> 채점 방식이 너그러워서 **삭제했다**. 무엇이 문제였는지와 다시 잰 결과는 3.8 절에 있다.
> 아래에는 채점 방식과 무관하게 유지되는 관찰만 남긴다.

팀원이 직접 찍은 실제 영수증 사진 5장. 감열지, 구김, 배경(키보드), 기울어짐, 옆으로 눕힌 사진이 섞여 있다.

| 영수증 | 특징 | 글자 줄 각도 |
|---|---|---|
| 육미안 | 심하게 구겨짐, 세트 하위 메뉴 | -2.7도 |
| 알베르(카페) | 옵션 줄이 금액 0 으로 찍힘 | -3.3도 |
| 이마트에브리데이 | 할인 줄(-5,000), 바코드 줄에 금액 | -0.3도 |
| 다이소 | **사진이 옆으로 누움** | +77.1도 |
| 이마트 죽전 | 품목마다 할인 줄, 바코드 줄에 금액 | -0.8도 |

### 알게 된 것

1. **기존 OpenCV 기울기 보정은 실제 사진에서 동작하지 않는다.** 육미안·알베르·다이소 모두 0.0도로 판단했다.
   원인: 영수증 바깥 배경(검은 키보드)이 이진화와 윤곽선 검출을 지배해, 글자 줄이 아니라
   자판 모서리 각도를 잡는다. 또 20도를 넘는 각도는 오검출로 간주해 버리도록 짜서 옆으로 누운 사진은
   원리적으로 처리할 수 없다. **합성 이미지에는 배경이 없어서 이 문제가 드러나지 않았다.**
2. **글자 상자 각도로 추정하면 정확하다.** OCR 검출 결과의 각 상자에서 긴 변의 방향을 구해
   중앙값을 내면, 배경과 무관하게 글자 줄의 각도가 나온다(위 표의 각도).
   단, 이 방법은 180도 뒤집힘을 구분하지 못한다. 다이소는 77도 회전 결과가 마침 바로 선 방향이었을 뿐이다.
   앱에서는 두 방향을 모두 인식해 보고 신뢰도가 높은 쪽을 고른다(다이소: 93.9% vs 69.1%).
   신뢰도는 이렇게 **방향 판정에만** 쓰고, 정확도 평가에는 쓰지 않는다.
3. **배경 글자가 섞인다.** 키보드 자판(Shift, Enter, PrtSc 등)이 글자로 검출됐다.
   영수증 영역만 잘라내면 사라진다(3.8 절).
4. 실제 영수증 사진에는 카드번호 일부·이름이 찍혀 있으므로 **공개 저장소에 올리지 않는다.**

## 3.8 전처리 조합 탐색 — 정답지 기반 채점 (2026-11-14)

채점 도구와 재현 방법은 `tools/ocr-eval/README.md`.
> 이 절은 1차(영수증 5장) 결과다. 팀원 영수증 11장으로 다시 검증한 결과와 **최종 결론은 3.9 절**에 있다.

### 이전 채점(3.7 초안)의 문제

| 문제 | 결과 |
|---|---|
| 글자 일치를 "일치한 글자 수" 로만 셌다 | OCR 이 **덧붙인 글자는 감점되지 않았다** |
| 정답 하나마다 가장 비슷한 상자를 따로 골랐다 | 같은 인식 상자를 여러 정답에 **중복 사용** 할 수 있었다 |
| 금액을 "문자열이 포함되는가" 로 봤다 | 정답 `1,000` 이 인식 결과 `11,000` 안에서 **찾은 것으로 처리** |
| 결과가 얼마나 흔들리는지 재지 않았다 | 몇 % 차이가 개선인지 우연인지 판단할 수 없었다 |
| 정답지를 사진과 대조해 검증하지 않았다 | 정답 자체가 틀렸을 가능성 |

### 정답지

- 사람이 사진을 보고 인쇄된 줄 순서대로 적었다. 5장 합계: 품목명 23개(189자), 숫자(금액·수량) 93개,
  거래일시 5개, 라벨(합계·부가세 등) 29개, 바코드 13개
- 인쇄 자체가 애매한 칸은 채점에서 뺐다. 예: 이마트 "죽전점" 은 인쇄가 "죽천점" 처럼 보인다.
  (3.7 초안에서 "죽전점→측천점" 을 OCR 오류로 적었던 것은 철회)
- 사진 옆에 정답을 나란히 붙인 **대조표 이미지** 로 다른 팀원이 실물 영수증과 맞춰 볼 수 있게 했다
- 개인정보(구매 내역)라서 저장소에 올리지 않는다

### 지표

| 지표 | 정의 | 왜 이렇게 |
|---|---|---|
| **숫자 정확** | 정답 금액·수량 중 한 자리도 틀리지 않고 읽은 개수. 독립된 숫자 토큰끼리만 비교. 같은 값이 여러 번이면 개수까지 맞아야 한다. 부호 구분(`-5,000` ≠ `5,000`) | 가계부에서 금액 오류가 가장 치명적. `1,000` 과 `11,000` 을 구분해야 한다 |
| | 제외: 글자에 붙은 숫자(`2인분` 의 2, `500mL`), 날짜, 전화번호, 바코드(10자리 이상) | 금액·수량이 아님 |
| **품목명 CER** | (삽입 + 삭제 + 치환) ÷ 정답 글자 수. 띄어쓰기만 무시. 인식 상자 하나는 정답 하나에만 쓴다. 한 품목이 상자 두 개로 쪼개졌으면 옆 상자를 붙인 것도 후보로 본다 | 덧붙인 글자도 오류다 |
| **줄 맞춤** | 각 줄의 기준(품목명·라벨·바코드)과 그 줄 금액이 OCR 결과에서 같은 높이에 있는가 (높이 차 < 글자 높이의 절반). 기준을 못 찾으면(CER > 34%) 실패 | 파서(P5)가 품목과 금액을 짝지으려면 이게 맞아야 한다 |

모델이 매기는 신뢰도는 쓰지 않았다. 아래 "남은 오류" 의 `솔밥` 은 신뢰도 99.8% 로 틀렸다.
채점기 자체는 테스트 17개로 확인했다(`1,000` vs `11,000`, `2인분`, 전화번호 `(031)` 등).

### 실험 설계

공통 1단계는 글자 상자 각도로 회전(3.7). 그 위에 5가지 요인을 모두 조합했다.

| 요인 | 수준 |
|---|---|
| 영수증만 자르기 | 끔 / 켬 (밝고 채도 낮은 영역 중 가장 큰 덩어리) |
| 색 | 컬러 / 흑백 |
| 톤 보정 | 없음 / 대비개선(CLAHE) / 그림자 보정(흐린 배경으로 나누기) / 이진화(적응형, 흑백 전용) |
| 선명화 | 끔 / 켬 (언샤프 마스크) |
| 글자 높이 | 32 / 48 / 64px 가 되도록 크기 조정 |

84개 조합 + 원본 + 회전만 = 86가지 × 5장 = 430회. 모두 **앱과 같은 브라우저 OCR**
(헤드리스 Chromium, 앱의 OCR 테스트 화면, 같은 모델·설정)로 돌렸다. 같은 입력이면 결과가 같다(결정적).

**잡음 기준선**: 회전만 한 이미지에 눈에 안 보이는 변화(2px 이동, 3% 확대, JPEG 95 재압축)를 줬더니
숫자 최대 4개, 줄 3개, 품목 오류 글자 3개가 흔들렸다. **이보다 작은 차이는 "차이 없음" 으로 본다.**

**선택 규칙 — 결과를 보기 전에 정했다**: 숫자 → 줄 맞춤 → 품목 오류 글자 순으로, 각 단계에서 최고치와
잡음 이내인 조합만 남기고 마지막에 가장 빠른 것을 고른다. 순서는 피해 크기 순이다(금액 오류 > 짝 오류 >
품목명 오류. 품목명은 검수 화면에서 고치기 가장 쉽다).

**교차검증**: 4장으로 고르고 남은 1장에서 확인하기를 5번.

### 그러나 93/93 은 대부분 운이다

육미안 세트 하위 메뉴의 `0  1  0` 4줄(숫자 12개)이 문제다.

- 회전만: 12개 중 2개. 눈에 안 보이는 변화만 줘도 2~6개 사이를 오간다
- 조합별로 육미안 숫자 정답 수가 10~22개로 퍼져 있다. 요인과 관계없이 거의 무작위다
- 교차검증에서 육미안을 빼고 고르면 다른 조합(흑백+대비개선)이 뽑히고, 그 조합은 육미안에서 14/22 (회전만 12, 원본 14)

그래서 이 12개를 빼고 다시 계산했다(민감도 분석, `groundtruth-sensitivity.json`). 잡음 기준선은 숫자 1개로 줄어든다.

| | 숫자 (81) | 줄 (43) | 품목 오류 글자 (189) | 시간 |
|---|---|---|---|---|
| 원본 그대로 | 67 | 26 | 61 | 9.6초 |
| 회전만 | 81 | 40 | 11 | 10.6초 |
| 회전 + 자르기 + 32px | 81 | 41 | 9 | 5.9초 |

선택 규칙은 그대로 같은 조합을 고른다. 교차검증(남은 1장에서 얻은 점수의 5장 합계):

| | 숫자 (81) | 줄 (43) | 품목 오류 글자 |
|---|---|---|---|
| 4장으로 고른 조합 | 80 | 42 | 12 |
| 회전만 | 81 | 40 | 11 |
| 원본 그대로 | 67 | 26 | 61 |

다이소를 빼고 고르면 이진화 조합이 뽑히고, 그 조합은 다이소에서 숫자 하나를 놓친다.
4장만으로 고르면 우연에 맞춘 조합이 뽑힐 수 있다는 뜻이다.

**정리**
- **정확도: 회전이 거의 전부다.** 원본 → 회전만으로 숫자 67 → 81, 줄 26 → 40, 오류 글자 61 → 11.
  회전 이후의 추가 전처리는 잡음 범위 안이다. 측정 가능한 정확도 개선은 없다.
- **속도: 자르기 + 32px 로 약 1.7배 빠르다.** 다른 작업 없이 다시 잰 값 10.3초 → 6.1초, 인식 결과는 동일.
  줄어든 것은 대부분 검출 시간(4.9초 → 1.2초)이다.

### 1차 결론 (3.9 절에서 흑백 여부만 바뀜)

1. 1차 인식(긴 변 1024px 로 줄인 사진) → 글자 상자 각도와 글자 높이 측정
2. 각도만큼 회전 (180도 뒤집힘은 3.7 의 방법으로 판정)
3. 영수증 영역만 자르기
4. 글자 높이가 32px 이 되도록 크기 조정
5. 그 외(톤 보정, 이진화, 선명화, 흑백 변환)는 **하지 않는다**
6. 2차 인식

**2차 인식 생략 조건 (구현 후 측정 예정)**: 각도가 1도 미만이면 1차 결과를 그대로 쓴다.
근거: 줄 묶기가 깨지려면 한 줄 양 끝의 높이 차가 글자 높이 절반을 넘어야 하는데, 영수증 한 줄 폭이 글자 높이의
약 20배이므로 atan(0.5 / 20) ≈ 1.4도. 실측으로 이마트 2장(-0.3도, -0.8도)은 1차 결과만으로 2차와 점수가 같았고,
알베르(-3.3도)는 1차만으로는 줄 맞춤 5/8(2차 8/8)이었다.

**처리 시간 주의**: SDK 에 "검출만" 하는 공개 API 가 없어서 1차 인식도 글자 인식까지 돈다(5~7초).
기울어진 사진은 1차 + 2차로 약 12초가 걸려, 지금(원본 1회 약 10초)보다 느려질 수 있다. 바로 찍은 사진은 1차만으로 끝난다.
구현 후 같은 채점기로 다시 재서 기록한다.

| 글자 48px | 190 | 52 | 27 |
| 글자 64px | 194 | 55 | 28 |

- 1차 선택 조합은 회전만·원본과 **잡음 범위 안에서 같다** (숫자 5개 차이 < 7). 잃은 숫자는 성심당·찜닭집·돈까스집의 한 자리 숫자(`1`·`2`·`5`·`6`)였는데,
  눈에 안 보이는 변화(3% 확대)만 줘도 같은 세 영수증에서 한 자리 숫자가 1~2개씩 빠졌다.
- 새 11장은 대부분 똑바로 찍혀서(배스킨 빼고 ±2.6도 이내) 원본과 회전만의 차이가 작다. **회전의 효과는 기울어진 사진에서만 나타난다.**
- **톤 보정은 이번에도 전부 해롭다.** 1차와 같은 순서(이진화 < 그림자 보정 < 대비개선 < 없음)로 재현됐다.
- **글자를 키우면 위험하다.** 배스킨 사진은 48·64px 에서 검출이 통째로 실패했다(숫자 0/4, 상자 0~4개). 영수증만 잘라내지 못해 사진 전체가
  커진 경우다(3253×4144). SDK 가 원본 해상도로 검출하므로(3절) 이미지가 클수록 느리고, 이 사진에서는 아예 실패했다. 32px 에서는 이런 실패가 없었다.

### 16장 전체로 다시 고르기

1차 5장 + 2차 11장 = 16장, 양쪽에 다 있는 16가지(원본·회전만 포함)로 같은 선택 규칙을 다시 돌렸다. 잡음 기준선: 숫자 ±9, 줄 ±8, 오류 글자 ±10.

| | 숫자 (303) | 줄 (109) | 품목 오류 글자 (430) | 날짜 (14)† | 시간* |
|---|---|---|---|---|---|
| 원본 그대로 | 273 | 80 | 84 (19.5%) | 13 | 9.0초 |
| 회전만 | 285 | 96 | 34 (7.9%) | 12 | 9.3초 |
| 회전 + 자르기 + 32px, 컬러 | 290 | 97 | 28 (6.5%) | 13 | 6.5초 |
| **회전 + 자르기 + 32px, 흑백** ← 규칙이 고른 것 | **294** | **97** | 29 (6.7%) | 13 | **6.4초** |

\* 실행 중 다른 작업이 겹친 시간이라 상대 비교용. 조용한 상태에서 다시 잰 값은 아래.
† 날짜가 없는 사진(주점, 위쪽 잘림)과 일본어 날짜(칼디)를 뺀 14장. 분석 출력의 분모가 16으로 잘못 찍히던 것을 고쳤다.

- 규칙의 1~3단계를 통과한 조합은 4개(위 표의 회전만·컬러·흑백 + 자르기 없이 32px)였고, 넷의 정확도는 잡음 범위 안에서 같다.
  마지막 단계(가장 빠른 것)에서 흑백이 컬러보다 0.1초 빨라 뽑혔다. **흑백과 컬러는 사실상 같다.** 흑백이 숫자를 조금 더 맞힌 것은
  1차(요인 평균 +1.2개)와 2차(+5개) 모두 같은 방향이지만, 둘 다 잡음 범위 안이다.
- 15장으로 고르고 남은 1장에서 확인하기를 16번 했다. **16번 모두 같은 조합(흑백)이 뽑혔다.** 1차(5장) 때는 남긴 영수증에 따라 이진화·대비개선
  조합이 뽑히기도 했는데, 장수가 늘면서 선택이 안정됐다.
- 육미안 세트 하위 메뉴 숫자 12개를 빼고 계산해도(민감도 분석) 같은 조합이 뽑히고, 남은 1장 점수의 합계는 숫자 283/291 (회전만 283, 원본 269),
  줄 97/109 (96, 80), 품목 오류 글자 29 (34, 84) 다.

### 처리 시간 (다른 작업 없이 다시 잼)

16장 × 3가지를 다른 작업 없이 다시 돌렸다. 인식 결과는 앞의 실행과 글자 하나까지 같았다(결정적).

| 16장 평균 | 전체 | 검출 | 인식 |
|---|---|---|---|
| 원본 그대로 | 9.8초 | 3.7초 | 5.9초 |
| 회전만 | 10.2초 | 4.1초 | 5.9초 |
| 회전 + 자르기 + 32px + 흑백 | **7.1초** | **1.2초** | 5.8초 |

- 줄어드는 것은 **검출 시간뿐**이다(4.1 → 1.2초). 인식은 글자 상자마다 따로 돌아서 상자 수에 비례하고, 전처리로 줄지 않는다.
  1차 5장에서는 1.7배였는데 16장 평균으로는 약 1.4배다. 원래 작은 사진(칼디, 돈까스집, 주점)은 줄일 것이 없어 이득이 없다.
- 이 값은 2차 인식 한 번의 시간이다. 앱에서는 각도를 재기 위한 1차 인식(작게 줄인 사진, 1차 5장에서 5~7초)이 앞에 붙는다.
  각도가 1도 미만이면 2차를 생략하는 조건(3.8)이 실제 체감 시간을 좌우한다.

### 일본어 영수증 — 인식 모델을 바꿔 보기

일본어 3장을 PaddleOCR 다국어 모델(`PP-OCRv5_mobile_rec`, 중국어·일본어·영어)로도 돌렸다. 앱 코드는 바꾸지 않고, 모델만 바꾼 임시 빌드로 같은
화면·같은 이미지를 썼다. 이 비교에서는 일본어 글자 칸도 채점했다(반각·전각 가타카나는 같은 글자로 봄).

| 회전만 기준, 3장 합계 | 한국어 모델 | 다국어 모델 |
|---|---|---|
| 숫자 (33) | 26 | 30 |
| 품목 오류 글자 (176) | 119 (68%) | 28 (16%) |
| 줄 맞춤 (31) | 0 | 21 |
| 날짜 (3) | 1 | 2 |

- 한국어 모델도 깨끗한 일본 영수증의 **금액은 읽는다**(칼디 21/21). 하지만 품목명·상호·`小計` 같은 라벨을 못 읽어 품목과 금액을 짝지을 수 없다.
- 바랜 규카츠 영수증은 한국어 모델로 숫자 1~3/8, 다국어 모델로 4~7/8 이었다.
- 3장뿐이라 수치보다는 방향만 본다. **4장 "언어별 인식 모델 전환" 이 필요하다는 근거**가 생겼다. 다국어 모델은 한글을 읽지 못하므로
  여행 지역에 따라 바꾸는 구조여야 한다.

### 최종 결론: 앱에 넣을 전처리

1. 1차 인식(긴 변 1024px 로 줄인 사진) → 글자 상자 각도와 글자 높이 측정
2. 각도만큼 회전 (180도 뒤집힘은 3.7 의 방법으로 판정)
3. 영수증 영역만 자르기 — 못 찾으면(밝은 천·나무 배경) 사진 전체를 그대로 쓴다. 정확도에는 영향 없고 속도 이득만 없다
4. 글자 높이 32px 로 크기 조정 — 48·64px 는 느리고, 큰 사진에서 검출이 통째로 실패할 수 있다
5. 흑백 변환 (컬러와 사실상 같음. 규칙대로 흑백)
6. 톤 보정·이진화·선명화는 **하지 않는다** — 1차·2차 모두 해롭거나 효과 없음
7. 2차 인식. 각도 1도 미만이면 2차 생략 (구현 후 측정 → 3.10)
8. 여행 지역이 일본이면 다국어 인식 모델로 바꾼다 (4장, 구현 → 3.10)

### 2차에서 새로 본 문제

| 문제 | 예 | 대응 |
|---|---|---|
| 모델이 흔한 단어로 "고쳐" 읽음 | 인쇄된 `깔루이밀크` → `깔루아밀크` | 정답지는 인쇄된 대로 두었다. 사용자에게는 오히려 맞는 경우라 검수 화면에서 판단 |
| 비슷한 글자 혼동 | 별퐁피자→별옹·별풍피자, 칵테일→칼테일, 치즈→치츠, 싱글레귤러→싱글레큘러, 공기밥→복기밥 | 검수 화면에 원본 조각 표시 (3.8) |
| 종이가 휘어 아래쪽 줄이 처짐 | 별빛퐁당 아래 3줄은 코드와 금액이 0.6~0.8줄 어긋남 | 회전으로는 못 고친다. 파서(P5)가 열 정렬 등으로 감안해야 함 |
| 감열지가 바램 | 규카츠: 어떤 전처리로도 숫자 1~3/8 (한국어 모델) | 다시 찍기·직접 입력 안내 |
| 영수증 자르기 실패 | 밝은 천(r9, r13)·나무(r10) 배경 | 사진 전체 사용(위 3번) |

### 한계

- 2차는 선명화를 빼고 15가지 조합만 돌렸다. 요인 전체를 다 바꿔 본 것은 1차(86가지)뿐이다
- 일본어 비교는 3장뿐이다
- 정답지는 한 사람이 적었다. 대조표(비공개 자료)로 팀원이 실물과 맞춰 봐야 한다

## 3.10 앱 구현과 앱 안에서 다시 잰 결과 (2026-11-16)

3.9 의 순서를 앱에 넣었다. 평가 도구는 파이썬으로 이미지를 미리 만들어 OCR 화면에 넣었지만, 이번에는
**앱이 사진 한 장을 받아 처음부터 끝까지 처리한 결과**를 같은 정답지·채점기로 채점했다.

| 파일 | 하는 일 |
|---|---|
| `src/ocr/pipeline.ts` | 1차 인식 → 각도·글자 높이 → (1도 이상이면) 전처리 + 2차 인식 → 위아래 확인 |
| `src/image/preprocess.ts` | 회전·영수증 자르기·크기 조정·흑백 (OpenCV.js, `tools/ocr-eval/pipeline.py` 를 그대로 옮김) |
| `src/image/geometry.ts` | 글자 상자로 각도·글자 높이 재기, 2차 생략·위아래 판정 (DOM 없음, 테스트 8개) |
| `src/ui/screens/scan.ts` | 사진 파일 선택 → 위 처리 → 읽은 글자 확인 → 저장 (인식에 쓴 이미지와 글자·좌표를 함께 저장) |

평가 때와 다른 점: 1차 인식을 원본이 아니라 **긴 변 1600px 로 줄인 사진**으로 한다(평가 때는 원본). 각도·글자 높이가
조금 다르게 나온다 (알베르 -3.6도 / 원본 -3.3도, 다이소 76.1 / 77.1도, 이마트 죽전 0.0 / -0.8도).

### 결과 (16장, 한국어 모델)

| | 숫자 (303) | 줄 (109) | 품목 오류 글자 (430) | 날짜 (14) | 평균 시간 | 인식 횟수 |
|---|---|---|---|---|---|---|
| 원본 그대로 1회 | 273 | 80 | 84 | 13 | 9.0초 | 1 |
| 평가 때 고른 조합 (이미지를 미리 만들어 1회)* | 294 | 97 | 29 | 13 | 6.4초 | 1 |
| **앱: 기울기 1도 미만이면 2차 생략** | **290** | **98** | **30** | 12 | **12.1초** | 1.6 |
| 앱: 항상 2차 | 295 | 98 | 30 | 12 | 15.6초 | 2.1 |

\* 이 줄의 시간은 미리 만든 이미지를 인식한 1회만이다. 실제로는 각도를 재는 1차 인식이 앞에 붙어야 한다.

- **앱 구현은 평가 때와 같은 정확도를 낸다** (잡음 ±9 안). 파이썬에서 고른 결과가 앱에 그대로 옮겨졌다.
- **시간은 원본 그대로보다 길다.** 기울기가 1도 미만인 8장은 1차 결과를 그대로 써서 4~9초(원본 1회와 비슷)였고,
  2차까지 돈 8장은 10~26초였다. 다이소처럼 옆으로 누운 사진은 위아래를 확인하느라 인식을 3번 해서 가장 길다.
  SDK 에 검출만 하는 공개 API 가 없어서, 각도만 재려는 1차에서도 글자 인식까지 도는 것이 원인이다.
  앱 평균에는 첫 장의 모델 로딩(약 4초)이 들어 있다.
- **2차 생략은 켠다.** 항상 2차를 돌려도 숫자 5개 차이(잡음 범위 안)였고 평균 3.5초가 더 걸렸다.
  생략했을 때 잃은 숫자 중 2개는 성심당이었다. 1차용으로 줄인 사진에서 글자가 20px 로 작았던 경우인데,
  이런 사진만 2차를 돌리는 조건은 같은 16장으로 정하면 과적합이라 넣지 않았다. 영수증이 더 모이면 확인한다.

## 4. 개선 포인트 (과목 평가 대응)

과목 평가 기준에 "오픈소스 재현 후 개선"이 있다. 이 프로젝트의 개선 지점은 두 가지다.

1. **한국 영수증 특화 전처리** — 공식 예제는 일반 장면 텍스트 기준이다. 실제 영수증 16장(1차 5장에서 고르고
   처음 보는 11장으로 검증)으로 측정한 결과(3.8·3.9 절), 글자 상자 각도 기반 회전이 정확도 개선의 대부분
   (16장 합계 숫자 273 → 285/303, 품목 오류 글자 84 → 34)을 차지했고, 자르기·글자 높이 32px 로 처리시간을 줄였다.
   흔히 쓰는 이진화·대비개선·그림자 보정은 두 번 다 오히려 해로웠다.
2. **언어별 인식 모델 전환** — 여행 영수증은 국내/해외가 섞인다. 여행 생성 시 지역을 고르면
   인식 모델을 바꾸는 구조로 간다. 한국 여행은 한국어 모델, 일본은 다국어(중·일·영) 모델, 라틴 문자권은
   PP-OCRv5 라틴 모델을 쓴다. 일본 영수증 3장에서 이미 차이를 확인했다(3.9 절: 품목 오류 글자 68% → 16%).

구조상 `src/ocr/models.ts` 의 `RECOGNITION_MODELS` 에 항목을 추가하면 되도록 열어 두었다.

| `model_name` 불일치 | 초기화 단계에서 오류 | `fetch-models.sh` 가 yml 값을 검증한다 |
| COOP/COEP 누락 | 추론이 느려짐 | 위 3절. P0 점검 화면에서 확인 |
| 브라우저 데이터 삭제 | 저장한 영수증 소실 | P2 에서 영구 저장 권한 요청, P6 에서 CSV 내보내기 제공 |
| wasm MIME 타입 | 스트리밍 컴파일 실패 | `nginx.conf` 에 `application/wasm` 지정함 |
| OpenCV.js 를 Vite 사전 번들링에서 제외 | **개발 서버(make dev)에서만** `does not provide an export named 'default'` 로 화면이 안 뜸. 빌드본은 정상이라 놓치기 쉽다 | `vite.config.ts` 의 `optimizeDeps.exclude` 에 OpenCV.js 를 넣지 않는다 (CommonJS 라 사전 번들링이 필요) |
| 큰 이미지 | 검출이 느리고, 아주 크면 글자를 하나도 못 찾음 | SDK 는 원본 해상도로 검출한다(3절). 전처리에서 글자 높이 32px 로 줄인다 (3.9) |

## 6. 라이선스

| 구성요소 | 라이선스 |
|---|---|
