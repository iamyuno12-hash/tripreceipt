# 개발 로드맵

웹(브라우저 단독) 기준 계획이다. 각 단계 끝에서 태그를 붙여 Git 로그에 단계 경계를 남긴다.

## 기본 구조

**백엔드가 없다.** OCR 추론, 이미지 전처리, 데이터 저장, 통계 집계가 모두 브라우저 안에서
일어난다. 서버는 정적 파일(HTML/JS/모델)을 내려주는 역할만 한다.

```
브라우저
 ├─ 입력      사진 파일 선택 (휴대폰에서는 선택 창에서 바로 촬영 가능)
 ├─ 전처리    OpenCV.js
 ├─ 추론      ONNX Runtime Web + PP-OCRv5 모델
 ├─ 파싱      자체 구현 (좌표 라인 그룹핑 → 금액 분리 → 교차검증)
 ├─ 저장      IndexedDB
 └─ 집계      여행별 / 카테고리별 통계

정적 서버 (nginx)  ← HTML, JS, OCR 모델(.tar) 만 제공. 데이터는 받지 않는다.
```

이 구성은 교수님이 조언하신 "백엔드 없이 내부 저장으로 간소화"를 그대로 만족하면서
제안서의 웹 서비스 형태도 유지한다.

### 범위 변경 (2026-11-16)

- **카메라 화면은 만들지 않는다.** 웹 서비스이므로 사진 파일 선택만 둔다. 휴대폰 브라우저에서는 파일 선택 창에서
  "사진 찍기" 를 고를 수 있어 촬영도 같은 경로로 된다. getUserMedia 촬영 코드와 카메라 권한 처리는 지웠다.
- **오프라인 동작은 목표에서 뺀다.** 웹으로 접속해 쓰는 서비스라 서비스 워커·모델 캐시 같은 오프라인 장치는 만들지 않는다.
  (외부 OCR API 를 쓰지 않고 브라우저 안에서 인식한다는 점은 그대로다)
- **외국어 인식을 P4 로 당겼다** (원래 P6). 일본 영수증에서 한국어 모델이 품목명을 거의 못 읽는 것을 확인했기 때문 (OCR-ENGINE.md 3.9).

### P3·P4 에서 구현한 내용 (2026-11-16)

- 사진 파일 선택 → 1차 인식으로 기울기·글자 높이 측정 → 회전·영수증 자르기·글자 높이 32px·흑백 → 2차 인식
  (기울기 1도 미만이면 2차 생략, 옆으로 누운 사진은 위아래를 두 방향 다 읽어 보고 결정) — `src/ocr/pipeline.ts`
- 여행마다 영수증 언어 선택 (한국어 / 일본어·중국어). 통화로 기본값을 추천 (엔·위안·대만달러·홍콩달러 → 일본어·중국어)
- 인식 결과(글자·좌표·처리 시간)를 영수증에 함께 저장, 영수증 상세 화면에서 "읽은 글자" 로 확인. 품목 자동 채우기는 P5
- OCR 테스트 화면이 앱과 같은 처리를 쓰도록 바꿈 → 평가 도구가 앱의 실제 동작을 그대로 채점

## 제안서 대비 변경점

| 항목 | 제안서 | 현재 | 사유 |
|---|---|---|---|
| 실행 형태 | Flask 웹 서비스 | 브라우저 단독 웹 앱 | 백엔드 축소 (교수님 조언) |
| 서버 | Flask (Python) | 정적 서버만 (nginx) | 데이터를 서버에 보내지 않음 |
| 데이터 저장 | 서버측 SQLite | 브라우저 IndexedDB | 동일하게 관계형 구조 유지, 위치만 단말로 |
| OCR 실행 위치 | 서버 (Python PaddleOCR) | 브라우저 (ONNX Runtime Web) | 백엔드 제거에 따른 변경 |
| OCR 엔진 | PaddleOCR | PaddleOCR (유지) | 제안서 기술 스택 유지 |
| 전처리 | OpenCV | OpenCV.js (유지) | 같은 라이브러리의 WASM 빌드 |
| 파싱 로직 | 자체 구현 (Python) | 자체 구현 (TypeScript) | 알고리즘 동일, 언어만 변경 |

**핵심**: 제안서의 기술적 기여(OpenCV 전처리 + 좌표 기반 파싱 + 품목합계 교차검증)는
그대로 유지된다. 바뀐 것은 실행 위치(서버 → 브라우저)뿐이며, 오히려 다음 장점이 생겼다.

- 영수증 사진이 네트워크로 나가지 않는다 (제안서가 내세운 개인정보 측면의 강점이 강화됨)
- 외부 OCR API 비용·호출 제한이 없다
- 서버 운영·배포 부담이 없어 시연이 단순하다

보고서에서는 이 점을 "백엔드 제거라는 제약을 설계 개선으로 전환"으로 서술하면 된다.

## 단계별 리스크

| 단계 | 리스크 | 대응 |
|---|---|---|
| P3 | 휴대폰마다 파일 선택 창이 다름 (특히 iOS Safari) | 표준 `<input type=file accept=image/*>` 만 사용. 시연은 Chrome 기준 |

| P4 | 첫 인식 때 모델 다운로드 (한국어 약 17MB, 일본어·중국어 약 21MB) | 캐시 헤더로 재방문 시 재다운로드 방지. 시연 전 미리 1회 로드 |
| P5 | 영수증 양식 편차로 파싱 실패 | 교차검증 실패 건은 검수 화면으로 보냄. 100% 자동화를 목표하지 않음 |

| 전반 | 브라우저 데이터 삭제 시 기록 소실 | P2 에서 영구 저장 권한 요청 + P6 의 CSV 내보내기로 백업 경로 제공 |
